## Gaps — what's still missing

The governance story splits cleanly: **runtime enforcement** (the hooks apx-agent already exposes) and **compliance posture** (cross-domain policy evaluation, violation tracking, owner accountability). The runtime layer is apx-agent's; the posture layer is [databricks-watchdog](https://github.com/stuagano/databricks-watchdog)'s. Integration > reimplementation.

## Picked: Watchdog integration

Swapping the pick from "policies library" to "Watchdog integration" because [databricks-watchdog](https://github.com/stuagano/databricks-watchdog) is the compliance posture layer for UC that already does cross-domain policy evaluation, ontology with inheritance, violation lifecycle, owner accountability, and AI agent governance as a first-class domain. Building a local policies library inside apx-agent would duplicate (worse) what watchdog already ships.

### The split

| Layer | Owner | Lives where |
|---|---|---|
| **Runtime hooks** — `input_guardrails`, `output_guardrails`, `before_tool`, `before_model`, etc. | apx-agent | `_compile.py` + `_callbacks.py` (already shipped) |
| **Compliance posture** — declarative policies, violation tracking, owner accountability, trends | watchdog | `databricks-watchdog` repo |
| **Bridge** — emit / consume / report between the two | apx-agent (this work) | new `_watchdog.py` module |

### Integration shape

Three concrete pieces:

1. **Emit agent metadata for watchdog crawls.** apx-agent already knows the resources an agent declares (UC functions, Genie spaces, serving endpoints, vector indexes — via `collect_resource_specs`). A helper that writes those plus instructions / tool descriptions / sub-agent endpoints to a stable location (an MLflow tag, a UC table, or a JSON document at a known endpoint path) lets watchdog's crawler pick them up alongside other UC assets.

2. **Consume watchdog policy decisions at runtime.** A `WatchdogGuard` adapter that calls watchdog's policy-evaluation surface (one of its 13 MCP tools, or a direct API) for a given operation context, and returns reject/allow/redact. Plugs into the existing `input_guardrails` / `before_tool` / `before_model` hooks. Cached per-resource so it doesn't add a network hop on every tool call.

3. **Report decisions back as violation signals.** When the runtime blocks something via a `WatchdogGuard`, log a violation back to watchdog so the compliance dashboard reflects what actually happened in production — not just static crawl results. Pairs naturally with the audit log helpers (item #2 in the recommended order).

### Resolved contracts (2026-05-19)

All three blocking questions answered. Implementation shipped.

| Contract | Mechanism | Module |
|---|---|---|
| Metadata for watchdog's crawler | UC tags on the registered model (`apx.agent.*`) | `set_uc_tags_for_agent` |
| Runtime policy decisions | Watchdog's MCP tools (streamable HTTP) | `make_mcp_transport(mcp_url, tool_name=...)` |
| Violation reports | INSERT into a watchdog-owned UC Delta table | `make_uc_violation_writer(violations_table, ws=...)` |

`make_watchdog_transport` bundles the MCP evaluate transport + UC violation writer into one callable that `WatchdogClient(transport=...)` consumes. The UC violation writer auto-creates the violations table on first use; the MCP transport invokes the configured tool via `mcp.client.streamable_http`. Tests use mocked transports/clients (570 passing).

Status: integration is real, not sketch. Verification against a live watchdog deployment is the remaining work — see `_watchdog.py`'s docstring for the expected MCP tool response shape (`{"action", "reason", "policy_id", "domain", "redacted_content", "metadata"}`) which the watchdog side needs to match.
