# Canary + hot-swap for Databricks Apps — design

This doc covers the Apps-target equivalents of `apx canary deploy /
analyze / promote / rollback` and `apx hot-swap`. The Model Serving
implementations of both predate this work and stay unchanged; the Apps
implementations are siblings that share CLI surface area via a
`--target {model-serving,apps}` flag (default `model-serving` —
preserves every existing call site verbatim).

Sibling docs:

- [`apps-vs-model-serving.md`](./apps-vs-model-serving.md) — when to
  pick each deploy target. This doc is the operational counterpart for
  the canary / hot-swap workflow that historically only lived on Model
  Serving.
- [`_canary.py`](../python/src/apx_agent/_canary.py) — current Model
  Serving canary primitives.
- [`_hot_swap.py`](../python/src/apx_agent/_hot_swap.py) — current
  Model Serving hot-swap primitives.

## 1. Why this is harder on Apps

Model Serving has two platform primitives that make canary trivial:

1. **One endpoint, many served entities, traffic split.** Multiple
   model versions live behind one URL with platform-level
   round-robin / weighted routing.
2. **Per-served-entity env_vars.** `update_config_and_wait` can rewrite
   environment variables on a single served entity; replicas restart
   and pick up the new env.

Databricks Apps has neither. An App is a single FastAPI process behind
a single URL. There is no platform router that can send 10% of traffic
to a sibling App. There is no per-replica env-var swap independent of
a redeploy. The Apps equivalents have to be built out of `databricks
bundle deploy` + multiple App resources + the operator's own routing
choice.

## 2. Canary options considered

### Option 1 — Multi-target bundle (chosen)

Each DAB target points the same source tree at a different App
resource:

```yaml
# databricks.yml (conceptual; the canary block is generated at runtime)
resources:
  apps:
    my-agent:
      name: my-agent             # prod App
      source_code_path: ./.build
targets:
  prod:
    default: true
  canary-feat-x:                 # generated by `apx canary deploy --target apps`
    resources:
      apps:
        my-agent:
          name: my-agent-canary-feat-x   # separate App, separate URL
```

`apx canary deploy --target apps --canary-version feat-x` writes the
`canary-feat-x` target block, runs `databricks bundle deploy --target
canary-feat-x`, then `bundle run`. Result: two Apps running side by
side at two distinct URLs.

`apx canary promote` re-runs `databricks bundle deploy --target prod`
with the canary's commit/source pinned; the prod App restarts off the
canary's tree.

`apx canary rollback` is the inverse — re-deploys `prod` from the
prior commit/tag captured at deploy time.

`apx canary analyze` reads MLflow traces over the lookback window (not
App logs — see §5) and partitions by an `apx.app.name` trace
attribute. Both Apps emit traces to the same MLflow experiment; the
partition is structured.

**What this does not give you:** platform-level traffic split. The
`--traffic 10` flag is a hint to the operator, not a routing
directive. Traffic between prod and canary is routed by whatever
mechanism is upstream — feature flag in the calling code, DNS weight,
explicit A/B at the client. This is the honest framing: Option 1 is a
**canary soak environment**, not "10% of production users". The
two-served-entities-with-split semantics from Model Serving has no
direct analog without Option 3 below.

### Option 2 — In-process traffic split

Each App reads a `CANARY_FRACTION` env var and routes that percentage
of inbound requests to a different LLM endpoint internally. Same
process, same App, same code path — only the LLM call diverges. Set
via `bundle var` so `--var canary_fraction=10` rewrites the env
without re-deploying the artifact.

Pros: simplest infra, no second App, no router. Same shape as
`apx hot-swap` but probabilistic.

Cons: only the LLM endpoint changes — the full code path (tools,
prompts, post-processing) is identical. So this isn't a canary of the
agent; it's a canary of the model. Useful as a primitive but doesn't
replace what Model Serving's canary did.

Verdict: implement as `apx hot-swap --target apps` (single deterministic
swap), not as `apx canary`. The probabilistic variant is future work
once we have a calling-code router that can read trace tags to attribute
outcomes.

### Option 3 — Front-door router App

A separate router App reads a routing config table from UC (or Lakebase),
forwards each request to one of N backing Apps weighted by the config.
Backing Apps are agent-version-pinned; routing decisions live in data.

Pros: actual platform-level traffic split, no upstream cooperation
needed, A/B test arbitrary versions.

Cons: extra moving piece (the router), extra latency hop, extra
permissions surface, extra failure mode. The router becomes the new
hot spot — it has to be canaried itself, which is recursive.

Verdict: the right end state for high-stakes A/B work but
disproportionate complexity for a v1. Document as future work.

## 3. Hot-swap options considered

### Option A — Bundle re-deploy with a different `--var` (chosen)

```bash
apx hot-swap --target apps --llm-endpoint databricks-claude-opus-4-7
```

Internally:

1. Read `databricks.yml`, find `variables.llm_endpoint_name` (or the
   user-configured var name).
2. Read the current value as `previous_value` (for the
   `AppsHotSwapResult.previous_model`).
3. Run `databricks bundle deploy --target <current> --var
   llm_endpoint_name=<NEW>`. The App restarts; the new env propagates.
4. Poll `databricks apps get <app-name>` until RUNNING.

The shape mirrors Model Serving's `hot_swap_model` — both rewrite a
single config value and trigger a controlled restart, both surface
the previous value for rollback.

Why not rewrite `databricks.yml` itself? Bundle vars are exactly the
right knob: out-of-band of the YAML, scoped to a single deploy,
captured in the deployment record. Rewriting the YAML drifts the
repo state from production state. Vars don't.

### Option B — Direct App env-var patch via REST API (future work)

The Apps API exposes a `PATCH /api/2.0/apps/<name>` that can edit
`config.env` directly. Faster than re-deploying because it skips the
bundle staging step.

Cons: bundle config drifts from running config. Next `bundle deploy`
silently reverts the patch. Bad ergonomic; matches the same trap
Model Serving has when operators bypass `databricks.agents.deploy`.

Document as future work once we have a state-reconciliation story
between bundle vars and direct API patches.

## 4. Public CLI surface

```bash
# Existing surface (Model Serving) preserved; --target defaults to model-serving.
apx canary deploy   --endpoint EP --model UC.NAME --version 4 --traffic 10
apx canary analyze  --endpoint EP --hours 24
apx canary promote  --endpoint EP --model UC.NAME --version 4
apx canary rollback --endpoint EP --model UC.NAME --version 3
apx hot-swap        --endpoint EP --model databricks-claude-opus-4-7

# New surface (Apps).
apx canary deploy   --target apps --canary-version feat-x --traffic 10
apx canary analyze  --target apps --hours 24
apx canary promote  --target apps --canary-version feat-x
apx canary rollback --target apps --canary-version prev-tag
apx hot-swap        --target apps --llm-endpoint databricks-claude-opus-4-7
```

Dispatch happens inside each click handler. No new top-level
subcommands; existing call sites work unmodified.

## 5. Analyze: traces not logs

The task draft said "query `databricks apps logs <app_name>`". That
endpoint returns unstructured stdout/stderr. Parsing it for request
count, p50/p95 latency, error count is fragile — every uvicorn /
FastAPI / app-code change can shift the format.

Both Apps emit MLflow traces to the same experiment via
`AgentServer(agent_type="ResponsesAgent")`. Each trace already carries
`mlflow.experimentId` and we add an `apx.app.name` tag on the
ResponsesAgent compile path so the partition is structured. The
implementation reuses ~80% of the existing `analyze_canary` machinery
in `_canary.py` — the only difference is the filter attribute
(`apx.app.name` instead of `apx.model.endpoint_version`).

Logs remain available as a fallback (`databricks apps logs <name>`)
for the case where traces aren't emitting — usually a wiring bug, not
a steady-state thing. The CLI surfaces a warning when zero traces
match the lookback window and points at the logs command.

## 6. Canary target naming

Generated target name: `canary-<sanitized-version>`. Sanitization:
lowercase, `_/.` → `-`, strip non-`[a-z0-9-]`. Examples:

- `--canary-version v0.4.2` → target `canary-v0-4-2`, App
  `<base>-canary-v0-4-2`
- `--canary-version 7f3ab9c` → target `canary-7f3ab9c`, App
  `<base>-canary-7f3ab9c`

The App name follows `<base-app-name>-canary-<version>`. Deterministic
so `promote` / `rollback` / `analyze` can locate the target without a
state file — operator passes `--canary-version` consistently.

## 7. YAML mutation strategy

Reuse the same approach already in `cli._auto_update_databricks_yml`:

1. `yaml.safe_load(path.read_text())` → `dict`
2. Mutate the parsed dict in-memory.
3. `yaml.safe_dump(doc, default_flow_style=False, sort_keys=False)`

Limitations (same as the existing auto-update path):

- Comments in `databricks.yml` are lost on rewrite. The framework's
  scaffolded YAMLs are comment-light; users with heavy comments
  should hand-curate or use the `--var` path.
- Anchors and aliases are normalized away. Not a regression — the
  existing auto-update path has the same constraint.

Why not Jinja or sed? The bundle doc is already YAML-shaped, the
top-level structure is well-defined, and there's no templating to
preserve. PyYAML round-trip is the lowest-risk path.

For canary deploy, the inserted target block uses overlay semantics:
the new target inherits everything from the base and overrides
`resources.apps.<bundle_key>.name` to the canary App name. This
matches how DAB target merging works.

## 8. Promote / rollback semantics

Both walk the same code path: re-deploy `prod` with the canary's
source tree. They differ in operator intent and what `--canary-version`
identifies.

- `promote --canary-version feat-x`: takes the canary tree as-is and
  ships it as prod. Optionally tears down the canary App
  (`--keep-canary` to skip teardown).
- `rollback --canary-version prev-tag`: re-deploys prod off a prior
  tagged tree (typically the version that was prod before the canary
  went up). Tears down the canary App if present.

Neither writes state files. Both require the operator to pass the
version explicitly. Reasoning: state files in a multi-developer
workflow create attribution bugs (who deployed what, when, from where).
The version label is the source of truth and it's already in the
operator's hands from the deploy step.

## 9. Trade-offs vs Model Serving canary

| Concern | Model Serving | Apps (this design) |
|---|---|---|
| Traffic split mechanism | Platform routing, weighted | Operator-controlled — calling code, DNS, feature flag |
| Time to canary up | 10–30 min (container build) | 1–3 min (`bundle deploy`) |
| Time to roll back | Seconds (config update) | Same as a re-deploy (1–3 min) |
| Two-versions-one-URL | Yes | No — two URLs |
| Partition analyze | By served entity name | By `apx.app.name` trace tag |
| State location | `serving_endpoints` config | `databricks.yml` + DAB target block |

The honest summary: Apps canary is a soak-environment workflow, not a
traffic-split workflow. For workloads that need real platform-level
routing, Model Serving is still the right pick (this is captured in
`apps-vs-model-serving.md` row "Traffic split / canary"). The
`--target apps` flow gives the operator a fast, predictable
deploy-the-new-version-alongside cycle plus structured trace-based
comparison — which covers most of the "does this version regress?"
question without the platform router.

## 10. Future work

- **In-process probabilistic LLM split** (Option 2). Implement once
  the calling code has tag-aware result attribution so
  `apx canary analyze` can tell which fraction came out of which side.
- **Front-door router App** (Option 3). The real fix for actual
  traffic split. Recursive canary problem (router itself needs to
  canary) so this needs a bootstrap story.
- **Direct App env-var patch via REST** (hot-swap Option B). Faster
  than re-deploy but needs config-drift reconciliation with bundle
  vars first.
- **Cross-target promote** (Apps canary → Model Serving prod). If a
  team uses Apps for fast iteration and Model Serving for prod, the
  promote step should be able to land in the other target. Out of
  scope here.
